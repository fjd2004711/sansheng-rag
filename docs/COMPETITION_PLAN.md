# 竞赛方案：可验证的多智能体编排调度平台（暂名“衡析 VeriFlow”）

> 赛题：大模型 Agent 工具编排调度平台。设计并实现面向多智能体（Multi-Agent）协作的编排、调度、执行与验证平台，对标 LobeHub、DeepSeek Harness 等 Agent Harness 框架，考察知识库定义与集成、Agent 团队定义、工作流编排、动态调度、自我循环（Self-Loop）、结果验证与反馈优化的全链路工程能力；围绕真实或模拟的复杂任务场景，交付可运行系统、技术方案和演示成果。
>
> **实现状态**：M1–M5 已实现并实测，见 [ORCHESTRATION.md](ORCHESTRATION.md)（实现说明、实测结果与没做的部分，其中“编译成 LangGraph”和“断点续跑”没有做）。以下为最初的构思与计划（2026-10-30 起草），落地前需和团队确认截止日期、人数与是否沿用本仓库。

## 1. 一句话定位

**一个把“多智能体协作”做成可声明、可调度、可验证、可回放的平台，用“带分析建议的调研报告”这一复杂任务来证明它。**

与对标框架的差异化不在“能不能让多个 Agent 对话”，而在三件它们普遍没做好的事：

1. **独立验证**：执行者的“我做完了”不算数，由平台强制的、与执行者隔离的核查员和确定性规则来判定。
2. **有界自循环**：失败先诊断类型，再按类型路由到对应的修复动作，轮次和预算都有上限，可证明会终止。
3. **动态调度**：调度器根据资源（搜索限流、模型并发、预算、截止时间）和中间结果（证据覆盖不足）在运行时增删任务、并行扇出。

## 2. 对标调研

| 框架 | 编排方式 | 强项 | 与赛题相关的缺口 |
|---|---|---|---|
| LobeHub（Agent 群组 / Group Chat） | 主管（supervisor）按成员描述和对话历史决定下一位发言者，返回空列表即结束；状态存 PostgreSQL `chat_groups` 表，配置放 jsonb | 产品化好，团队定义直观，支持公开发言与私信 | 以对话轮转为核心，**没有 DAG 工作流、并发调度、结果验证**；终止由主管模型自行判断 |
| DeepSeek Harness（dsh，2026 年开源，开发者预览） | Cordis 插件框架：模型、工具、技能、会话、沙箱、存储、循环、调度都是插件；会话为追加式轨迹日志，可恢复、分叉、回放 | 插件化与可替换性强，轨迹可回放 | 偏单 Agent 编码场景，多智能体只到“子智能体调度”，**没有独立验证机制** |
| LangGraph / CrewAI / AutoGen | 显式状态图 / 角色-任务-团队 / 多种对话模式 | 编排原语成熟 | 验证、预算、调度需自建；自我报告即结果 |

结论：近期关于 Agent Harness 的综述和论文都指出，**“执行者自报完成”与“独立核查”的差距是主要可靠性缺口**，有界循环（预先的花费上限、可证明终止、经核验的完成）是公认方向。本方案把它作为主打点。

参考：[LobeHub RFC 130](https://lobehub.com/blog/rfc-130)、[LobeHub Agent 团队文档](https://lobehub.com/ja/docs/usage/agent/agent-team)、[DeepSeek Harness 插件架构解读](https://betterstack.com/community/guides/ai/deepseek-harness-plugin/)、[Bounded Loops（arXiv）](https://arxiv.org/pdf/2609.27871)、[Agent Harness 综述](https://agentic-ai.readthedocs.io/en/latest/AgentHarness/llm-harness-survey/)。

## 3. 任务场景

**主场景：政策 / 行业调研分析报告**（例：“2025 届大学生就业情况怎么样，学校和地方该怎么做？”）。

为什么选它：

- **真复杂**：规划提纲 → 多路检索权威资料 → 摘取并核对数据 → 分章撰写 → 逐条核验 → 补证 → 综合研判 → 行动建议，天然多角色、可并行、有依赖。
- **可验证**：每个数字能逐字对到来源原文，每条说法有“已核实 / 单一来源 / 有争议 / 未能核实”的等级，结果好坏可量化。
- **有积累**：本仓库已有报告流水线、查证金标集、核验规则和一次服务器实测，实测暴露的问题（证据面窄、18 分钟耗时、建议依据分级不一致）正好由“动态调度”和“自循环”来解决，演示有前后对比。

**第二场景（证明平台通用，而非写死报告）**：知识库问答 + 纠错（本仓库 P0–P5 已有），或“竞品 / 政策对比表”。只需换一套团队和工作流定义，不改平台代码。

## 4. 平台架构

```
┌──────────── 定义层（声明式 Spec，版本化存 PostgreSQL） ────────────┐
│ 知识库 KB │ Agent │ 团队 Team │ 工作流 Workflow │ 策略 Policy（预算/门控/循环）│
└──────────────────────────────┬──────────────────────────────────┘
                     编译 ↓（校验 + 生成执行图）
┌──────── 编排层：Workflow → LangGraph 状态图（只管状态、路由、有界循环）────────┐
└──────────────────────────────┬──────────────────────────────────┘
┌──────── 调度层：就绪集 + 优先队列 + 资源池（搜索/模型并发、预算、截止时间）────────┐
│ 动态扇出 · 运行时插入/取消任务 · 模型路由 · 重试/超时 · 断点续跑                │
└──────────────────────────────┬──────────────────────────────────┘
┌──────── 执行层：Agent 运行时（LangChain）+ 工具注册表（检索/网页/抓取/计算/MCP）────┐
└──────────────────────────────┬──────────────────────────────────┘
┌──────── 验证与反馈层：独立核查员 + 确定性规则 + 质量门 + 失败诊断 → 自循环路由 ────┐
│ 金标评测 · 用户反馈 · 失败统计 → 策略/提示词/检索模板优化（回归门控）             │
└──────────────────────────────┬──────────────────────────────────┘
┌──────── 可观测层：结构化轨迹事件 · 时间线甘特图 · 成本 · 回放与分叉 ────────┐
```

技术栈沿用本仓库：FastAPI、PostgreSQL、Qdrant、LangChain（主框架）、LangGraph（仅状态/路由/有界循环，遵守 `ARCHITECTURE.md` 边界）、Next.js + React Flow（工作流画布已在依赖中）+ ECharts。

### 4.1 知识库定义与集成

```yaml
kind: KnowledgeBase
name: employment-official
sources:
  - type: web_search          # 走 SearXNG，可指定权威站点优先
    prefer_sites: [moe.gov.cn, mohrss.gov.cn, stats.gov.cn]
  - type: collection          # 已有 Qdrant 集合（上传的 PDF/DOCX）
    id: policy-docs-2025
retrieval: { dense: true, bm25: true, fusion: rrf, reranker: true, top_k: 12 }
credibility: { tiers: [authoritative, reference, general, low] }
freshness_days: 365
```

一个 Agent 可绑定多个知识库；检索结果统一为带编号、可信度等级和发布时间的证据，供核验链路追溯。

### 4.2 Agent 与团队定义

```yaml
kind: Agent
name: verifier
role: 独立核查员
model: { tier: strong }                  # 与撰稿人使用不同模型或不同提示，执行者与核查者隔离
tools: [read_evidence, number_check, independence_check, entailment_check]
knowledge: [employment-official]
can_see: [draft_text, evidence]          # 看不到撰稿人的推理过程
budget: { max_tokens: 40000 }
---
kind: Team
name: research-report-team
members: [planner, researcher*3, data_checker, writer, verifier, analyst, editor]
supervisor: planner
```

报告团队角色：规划师（拆提纲、定指标）→ 检索员 ×N（并行检索阅读）→ 数据核对员（摘数据并逐字比对原文）→ 撰稿人（分章写作）→ 核查员（逐条核验，独立）→ 分析师（综合研判与建议）→ 主编（统稿、范围分层、终审门）。

### 4.3 工作流编排

节点类型：`agent`（单步任务）、`map`（按提纲动态扇出）、`gate`（质量门，不过就进入循环）、`loop`（有界修复）、`human`（可选人工确认）、`merge`（汇总）。

```yaml
kind: Workflow
name: verified-report
nodes:
  plan:      { agent: planner }
  research:  { map: plan.sections, agent: researcher }
  extract:   { map: research, agent: data_checker }
  write:     { map: extract, agent: writer }
  verify:    { map: write, agent: verifier }
  gate_sec:  { gate: verify, pass_if: "false_pass_risk == 0 and coverage >= 0.6", on_fail: repair }
  repair:    { loop: max_rounds=2, route_by: failure_type }
  synth:     { agent: analyst, after: [gate_sec] }
  verify_syn:{ agent: verifier, input: synth }
  final:     { agent: editor, gate: "national_scope_present or scope_disclosed" }
```

前端用 React Flow 画布可视化编辑与查看，运行时节点实时着色（排队 / 运行 / 通过 / 修复中 / 失败）。

### 4.4 动态调度

- **就绪集调度**：依赖满足的节点入优先队列；`map` 节点在运行时根据提纲数量扇出，各章节并行。
- **资源池**：搜索并发（免费搜索易被限流，默认 2）、模型并发、每次运行的 token 与时长预算分别限额；超限排队而不是失败。
- **模型路由**：抽取、改写等轻任务走便宜快模型，核查与综合研判走强模型；某模型 403 / 超时自动降级到备选（这次实测的额度耗尽问题即属此类）。
- **运行时改计划**：核查后若某章证据覆盖不足或缺少全国口径，调度器插入“定向补检索”任务；预算将尽时取消低优先级章节的补证并在报告里披露。
- **可靠性**：任务级重试与超时、运行状态持久化、断线续跑（现在断线会让报告失败）。

目标：同主题报告从 18 分钟降到 6 分钟以内（章节并行 + 轻任务降级模型）。

### 4.5 自我循环（Self-Loop）

先诊断、再修复、有上限：

| 失败类型（由核查员和规则判定） | 修复动作 | 上限 |
|---|---|---|
| 证据不足 / 只有单一来源 | 定向补检索（权威站点优先）后重新核验 | 1 轮 |
| 数字与原文不符 | 用已核对数据重写该句 | 1 轮 |
| 范围错置（单校数据写成全国） | 改写并标注范围，或移出核心结论 | 1 轮 |
| 引用编号错配 | 重新挑选支持来源 | 1 轮 |
| 无来源支持的说法 / 疑似幻觉 | 删除或改为“公开资料中未找到” | 1 轮 |
| 修复后仍不通过 | 停止循环，在“争议与不确定”中披露 | — |

每次运行有总轮次与总预算上限，循环可证明终止；每轮修复都写入轨迹，可在前端回放“为什么改、改了什么”。

### 4.6 结果验证与反馈优化

- **独立验证**：确定性规则（数字逐字核对、万/亿与英文数量级换算、年份与指标冲突、转载同源判定）+ 隔离的核查员 + 蕴含复核（解决“数字对、指标错”）。
- **质量门**：每章、综合研判、终稿各一道门，门的条件写在 Policy 里而不是代码里。
- **反馈优化闭环**：
  1. 用户反馈（已有 👍👎 与原因）和核查失败统计按失败类型聚合；
  2. 自动生成改进候选（提示词变体、检索模板、权威站点表、路由阈值）；
  3. 在金标集上跑对比评测，**只有指标不退步才发布**（回归门控）；
  4. 发布的策略版本可在每份报告的方法说明里追溯。

## 6. 评测设计（评委最看重“用数据说话”）

- **任务指标**：说法已核实率、假通过率、全国口径覆盖率、建议依据强度分布、终稿通过质量门的比例。
- **工程指标**：端到端耗时、并行加速比、token 成本、平均修复轮次、失败恢复成功率。
- **消融实验**（同一主题集，多次重复并给出 95% 区间）：
  1. 单 Agent 一次生成；
  2. 多 Agent 无核查；
  3. 多 Agent + 核查、无自循环；
  4. 完整平台（核查 + 自循环 + 动态调度）。
- **主题集**：10–20 个调研主题（就业、人口、产业、医疗等），所有指标由脚本生成，不手写。

## 7. 演示脚本（约 8 分钟）

1. 在画布上展示报告团队和工作流定义（YAML 与图双向同步）。
2. 提交主题，实时看调度：章节并行扇出、搜索限流排队、某模型失败自动降级。
3. 核查员拦下“单校数据写成全国”，自循环补检索并改写，回放修复轨迹。
4. 终稿：核心结论、各章、综合研判、行动建议（带依据强度），一键导出 Word/PDF。
5. 换一套团队定义跑第二场景，证明平台通用。
6. 展示消融评测图表和反馈优化前后的指标对比。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型额度 / 接口不稳（实测已发生） | 多模型路由与自动降级；评测固定模型与种子并记录版本 |
| 免费搜索被限流 | 调度器限速排队；缓存检索结果；准备付费搜索源备选 |
| 平台做得太泛、演示不聚焦 | 主场景做深，第二场景只证明“换定义即可” |
| LangGraph 被扩张成领域层 | 编译器只生成状态与路由，Agent 逻辑留在 LangChain 执行层 |
| 指标好看但不可信 | 所有指标脚本生成、给出置信区间；保留留出集 |
