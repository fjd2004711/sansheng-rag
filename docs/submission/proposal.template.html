卷　首摘　要

让多个大模型分工完成一件复杂的事，如今并不困难；难的是最后一步：负责写的 Agent 宣布“完成了，数据都有出处”，平台凭什么相信它？我们在做检索问答时吃过这样的亏：回答里的数字带着整齐的引用编号，逐条点开来源，却发现有的数字原文里根本没有，有的把“141178 万”读成了“1.41 亿”，有的把一所学校的数据写成了“全国”。多 Agent 协作会把这种“自己给自己打分”的问题层层放大。

三省就是为这个问题设计的多智能体编排调度平台。它用一份 YAML 声明知识库、Agent、团队、工作流和策略；调度器按依赖、优先级和资源池并行执行，并在运行时按真实数据扇出任务、插入修复任务；执行者交出的成果不算数，要由与之隔离的独立核查员重新取证、逐条分级，再过一道由策略定义的质量门；不达标就先诊断失败类型、再按类型修复，修复只有“不比原稿差”才被采用，轮次、预算和“有没有进展”都设有上限，循环必然终止。全过程落成结构化事件，界面上可以实时观看，事后可以回放。名字取自唐代三省制：中书起草、门下审核（可“封驳”退回）、尚书执行。

我们以“带分析与行动建议的调研报告”为主场景，并用同一套平台、换一份定义跑通了第二个场景“事实核查”，没有改动平台代码。仓库中保存的最新版本运行里，一份完整报告用时 {{p9.wall_text}}（无需修复）到 {{p8.wall_text}}（修复一轮），并行度 {{p9.speedup}}～{{p8.speedup}} 倍；同一主题从初版的 {{evo_first.wall_seconds}} 秒降到 {{evo_last.wall_seconds}} 秒。{{runs_n}} 次真实运行里，质量门最终通过 {{d.gate_passed_final}} 次，未通过的 {{gate_failed}} 次如实标注“未达标”后交付，而不是假装通过。说法分级在两套金标集上没有出现把错误说法判为“已核实”的情况，但样本量有限，文中给出区间与不足。

卷　一一、选题背景与场景需求分析

本章要点
  • 多 Agent 流水线里，每一环都“自报通过”，最终结果没人真正检查过——这是我们要解决的核心问题。
  • 主场景选“带分析与行动建议的调研报告”：真复杂、可量化验证、有现实需求；第二场景“事实核查”证明平台通用。
  • 差异化不在“能不能让多个 Agent 对话”，而在独立核查、有界自循环和动态调度三件事做成平台的默认行为。

1.1 问题：谁来说它做完了

让一组大模型分工协作已是常见做法：一个拆任务，几个查资料，一个写，一个汇总。写一个能跑起来的多 Agent 演示，大半天就够。但真正拿去交付一件事，比如一份会被引用的调研报告，最让人不踏实的不是“能不能跑通”，而是最后那一句“完成”可不可信。

我们的体会来自自己做过的问答模块：检索和生成都很顺，每句话后面都有引用编号；逐条核对后才发现数字对不上、单位换算错、范围写大。模型并非有意，它只是在给自己的输出打高分。把这种结构放进多 Agent 流水线，规划员说提纲合理，检索员说资料充足，撰稿员说数据有出处，每一环都自报通过。因此平台的设计重心放在三件事上：成果必须由与执行者隔离的角色独立核查；核查不通过时先诊断、再有针对性地修复，修复的次数、花费和是否有进展都有界；调度能根据资源和中间结果在运行时调整计划。这三点正是赛题中“动态调度”“自我循环”“结果验证与反馈优化”的落脚点。

1.2 场景：政策与行业调研分析报告

典型输入是一句话主题，如“2025 届高校毕业生规模与就业情况”“2025 年中国新能源汽车销量与渗透率情况”。选它有三个原因。其一，它确实复杂：规划提纲、多路联网检索、摘取数据、分章撰写、逐条核验、补充证据、综合研判、给出建议，天然多角色、可并行、有依赖。其二，它可验证：每个数字都能逐字对到来源原文，每条说法可按“已核实 / 单一来源 / 有争议 / 未能核实”分级，好坏可以量化。其三，它有现实需求：学校、地方部门和行业研究者常要在短时间内拿出一份有出处的情况分析，既怕漏，更怕错。

为证明平台不是为报告写死的，我们同时提供第二个场景事实核查：用户粘贴一段含数字的文字，平台逐条抽取事实性说法、联网查证，输出带出处和等级的核查表。两个场景共用同一套调度器、核查员和质量门，只是定义不同。

1.5 名字的由来

唐代三省制中，中书省起草诏令，门下省审核，认为不妥可以“封驳”，把诏令原样退回；尚书省执行。起草的不审，审的不执行，靠相互制衡立得住。这恰好回答了“谁来说它做完了”：不能是写它的人。平台中的分工与之对应如下；界面上名字旁的“ⓘ”可以看到这段说明。这只是帮助理解分工的类比：门下省封驳整份诏令，我们的核查员逐条说法地审；古代长官也不会因“预算用完”而停下，我们的调度器会。

2.2 一次报告运行的数据流

  1. 用户在界面选择工作流、输入主题，可为整次运行或单个 Agent 指定模型；后端解析定义、写入运行记录，在后台任务中启动引擎。
  2. 规划师产出提纲、每章检索词与全国口径补充检索词；检索员按批次并行搜索并抓取网页，写入本次运行专用的 Qdrant 临时集合。
  3. 撰稿人按章并行取证、摘取数据点并与原文逐字核对后写作；同时，全国口径检索作为非必要旁支并行进行。
  4. 核查员按章流水线跟进：第 i 章一写完就独立重新取证、逐条分级，不等其他章节。
  5. 质量门汇总四项指标；不达标就在运行中插入“补检索”和“逐章重写并复核”两组任务，等它们完成后复查。
  6. 分析师写核心结论、综合研判和行动建议（建议的事实性前提再核验一次）；主编统稿，披露范围与不确定，生成证据核实图。
  7. 每一步都以事件落库；前端从事件推导画布、时间线、质量门面板，运行结束后可完整回放，报告可导出 Word / PDF。

2.4 为什么自研调度器，而不是把工作流编译成 LangGraph

起草方案时我们确实打算把工作流编译成 LangGraph 状态图。动手后发现，平台需要的几件事都要在运行期改变图的形状：map 节点要等上游产出后才知道扇出成几个任务（章节数、搜索批次数）；搜索和模型两类资源要分别限流；质量门不达标时要在运行中追加“补检索”“逐章重写”两组任务；核查要对撰写逐项流水线。这些用静态图表达都很别扭。于是 LangGraph 保留在它擅长的问答纠错状态机里，工作流层改为约 {{sched_lines}} 行的自研调度器。它换来了直接的并行与资源控制，也让调度器能脱离业务单独测试（4.1）。

卷　三三、Agent 角色定义、工作流设计与编排逻辑

本章要点
  • 五类声明对象写在同一份 YAML 里；导入时校验 9 类错误，其中“核查员读取执行者推理”会被直接拒绝。
  • 报告团队 7 个角色，原则是“一个角色一种责任、一类可见信息”；报告工作流 9 个节点，含两条旁支。
  • 换一份定义（4 个角色、4 个节点）就得到事实核查场景，平台代码不变。

3.1 声明式定义

平台用五类对象描述一个场景：知识库（检索来源、优先站点、检索链、时效）、Agent（角色、技能、模型档位、工具、可读信息、是否独立）、团队（成员与主管）、工作流（节点与依赖）和策略（预算、并发、修复轮次，作为工作流的一部分）。下面是内置报告定义的节选（完整定义见仓库 builtin.py）。

kind: KnowledgeBase
name: official-web
sources: [{type: web_search}]
prefer_sites: [moe.gov.cn, mohrss.gov.cn, stats.gov.cn, gov.cn]
retrieval: {dense: true, bm25: true, fusion: rrf, reranker: true}
freshness_days: 365
---
kind: Agent
name: verifier
role: 独立核查员
skill: verify_report
model_tier: strong
independent: true
can_see: [draft, evidence]        # 写成 [draft, reasoning] 会在导入时被拒绝
tools: [number_check, independence_check, claim_audit]
---
kind: Workflow
name: verified-report
policy: {max_tokens: 1500000, max_seconds: 2400, max_repair_rounds: 2, search_concurrency: 3, llm_concurrency: 6}
nodes:
  - {id: sections, kind: map, agent: writer,   depends_on: [search],   map_over: sections, pool: llm}
  - {id: verify,   kind: map, agent: verifier, depends_on: [sections], map_over: sections, pipeline: true, pool: llm}
  - id: gate_sections
    kind: gate
    depends_on: [verify, search_national]
    on_fail: repair
    gate: {min_verified_ratio: 0.5, max_unsupported_numbers: 0, require_scope_disclosed: true, min_authoritative_sections: 0.5}
  - {id: repair, kind: loop, agent: repairer, essential: false, max_rounds: 2}

3.2 定义校验：把“独立”写成强制规则

校验不只检查格式，还拦下会让运行失去意义的错误：节点 id 重复；依赖不存在的节点；依赖成环；质量门没有阈值；on_fail 指向不存在的节点或出现在非质量门节点上；团队成员没有 Agent 定义；节点使用的 Agent 不在团队里；Agent 引用了不存在的知识库；以及独立核查员的可读信息里包含执行者的推理过程。最后一条是“独立”不只是一个名字的保证：如果核查员读到撰稿人的推理，它很容易顺着同一思路得出同样结论，核查就成了复读。数值字段也有上下限，例如单个节点的修复轮次不超过 3、策略的修复轮次不超过 4、模型并发不超过 16。

3.5 编排逻辑

编译。引擎把每个节点编译成调度器里的一个“组”（Group）：声明它依赖哪些组、如何展开成任务、用哪个资源池、优先级多少、是否必要。调度器只看这些属性，不认识任何业务概念。

扇出时机。章节数和检索批次数不是写死的，而是规划师产出后才知道，所以 map 节点要等上游完成才按真实数据展开。在保存的最新运行里，规划后展开了 {{p8.search_batches}} 个检索批次和 {{p8.sections}} 个章节。

旁支。search_national 把“官方发布的全国口径数据”单独拉出来，与撰写并行，标记为非必要，预算吃紧时可被丢弃；质量门要等它，撰写不等它。这是针对早期运行里“只搜到单校数据却写成全国”的问题加的。

逐项流水线。pipeline: true 让核查第 i 章只依赖撰写第 i 章：写完一章核一章，写作与核查交错进行；上游某一项失败时，下游对应项记为失败，整组不会被误判成功。

用户可以调整什么。在“工作流定义”页可直接编辑 YAML：增删节点、调依赖、改质量门阈值与修复轮次、为 Agent 指定模型，校验通过后画布刷新，另存为自己的版本即可在新建运行时选用。实验中的“串行对照”就是这样建的：同一定义，只把两类并发上限改为 1。

卷　四四、调度算法与自我循环机制

本章要点
  • 调度器只有“任务”和“组”两种对象：就绪集按（优先级，入队时间）排序，在资源池信号量下执行。
  • 同一定义起草阶段串行 {{sp.serial_seconds}} 秒、并行 {{sp.parallel_seconds}} 秒，实测加速 {{sp.speedup}} 倍；同一主题七个版本从 {{evo_first.wall_seconds}} 秒降到 {{evo_last.wall_seconds}} 秒。
  • 自循环由质量门触发、按失败类型修复；重写“不比原稿差才采用”，四条终止条件保证必然结束。

4.1 调度器

任务（Task）有优先级、资源池、重试次数、超时、是否必要以及逐项依赖 needs；组（Group）有依赖、展开函数、优先级与是否逐项流水线。主循环如下：

loop:
  for g in groups:                                  # 展开：依赖满足的组按真实数据生成任务
      if not g.expanded and deps_ok(g): g.tasks = await g.expand()
  skip_blocked()                                    # 上游失败的组 / 逐项上游失败的任务直接跳过
  ready = [t for t in tasks if t.pending and needs_done(t)]
  for t in sorted(ready, key=(t.priority, t.queued_at)):
      if not t.essential and not budget_ok(): skip(t, "budget"); continue
      launch(execute(t))                            # 在 t.pool 的信号量下执行
  if nothing running and nothing pending: break
  await first_completed(running) or wake_event      # 任一任务结束，或有组被插入时醒来

4.4 自我循环

自循环由质量门触发。门的四项指标由纯函数计算：已核实说法占比、有权威来源支持的章节占比、来源原文里找不到的数字个数、范围错置的章节数（只有单个学校或地区的数据，却没声明不代表整体）。任一项不达标，门就不通过，并给出按章节归类的失败项。

失败类型判定修复动作

终止条件满足任一即结束：① 质量门通过；② 一轮修复后已核实比例提升不到 1 个百分点（无进展）；③ 达到最大修复轮数（节点与策略取较小者，内置为 2，校验上限分别为 3 和 4）；④ 预算已用掉 60%，不再开始新一轮。由于每轮都使有限的轮次计数加一，而上界在定义校验时已固定，循环必然终止，不依赖模型自己判断“差不多了”。没通过时，平台交付稿件并在“争议与不确定”中写明，而不是绕过。

4.5 采用条件的来历与实际作用

“重写不比原稿差才采用”和“无进展即停”不是一开始就有的。第一次用真实主题跑完整流程时，旧版自循环跑了 2 轮、多花约 14 分钟，已核实比例反而从 {{old.verified_first}}% 降到 {{old.verified_final}}%：重写把原本站得住的句子改坏了。这件事让我们把两条规则写进机制，而不是靠提示词劝模型“小心一点”。

在最新一次运行里，这条规则确实起了作用：首检已核实 {{p8.verified_first}}%，低于 50% 的门槛；修复阶段对 5 章尝试重写，复核后 {{p8.repairs_rejected}} 章不如原稿被放弃，{{p8.repairs_accepted}} 章被采用；复查已核实 {{p8.verified_final}}%，放行。没有这条规则，那 {{p8.repairs_rejected}} 章会被改得更差（图 7）。

卷　五五、结果验证策略与反馈优化逻辑

本章要点
  • 验证分四层：数据点逐字核对 → 说法规则分级 → 逐条独立复核 → 质量门。模型只负责“提取事实”，等级由规则给出。
  • 验证本身也被验证：两套金标集上假通过为 0（样本有限），抽取召回 77%–88% 是目前的主要缺口。
  • 反馈优化目前做到“按失败类型与用户反馈给出改进提示”，不会自动改策略上线。

5.1 四层验证

第一层：数据点逐字核对。撰稿人摘取数字时必须给出来源编号和来源里陈述它的那句原话；系统核对原话是否逐字出现在来源文本中，不过就丢弃。报告里的数据表、趋势图和证据核实图只用通过这一关的数据点，图里每个数字都能追到原文。

第二层：说法规则分级。正文被拆成原子说法，模型只指出“哪些来源支持、哪些反对、是否有时效”，等级由固定规则判定（表 11）。来源按权威、参考、一般、低四级分层；同一内容被多站转载算同一来源，不能凑数；来源文本必须带有说法中的数字才算支持。

第三层：逐条独立复核。“某来源支持某说法”是抽取时同一次模型调用给出的，等于自己给自己打分。所以每条说法再单独、带着来源完整段落问一次：是否陈述了同一个对象、指标、时间范围且数字一致。一个来源要两次被否决才剔除，以压住单次随机误判；被剔除的来源不算支持，但也不会被当成反对，避免制造假争议；调用失败则保留原判断。

第四层：质量门。汇总前三层结果算出四项指标，对照策略阈值，决定放行还是触发修复（4.4）。核查员对每一章重新取证分级，结果比撰稿时差就下调——最新运行里下调了 {{p8.downgrades}} 条。

7.6 局限与不足

  • 样本量。每个版本每个主题只有一次运行，金标集几十个用例，指标是实测值但不具统计显著性；没有做人工盲评。
  • 单一模型。撰写、核查、复核、评测用同一个模型，模型自身的盲点可能被同时放过；强 / 快两档目前指向同一模型。
  • 验证覆盖面。说法抽取召回 77%–88%，未被抽出的说法没有被核查。
  • 搜索。免费搜索会限流；证据面窄时修复帮不上忙，质量门如实报“未通过”。
  • 断点续跑未做。状态与事件已持久化，但中断后需整体重跑（服务启动时会把遗留运行标为中断，可一键重新运行）。
  • 不能拖拽拼装。定义靠 YAML 编辑，可用的技能是内置的一组。
  • 反馈优化只到提示。见 5.5。

8.1 用到的模型

8.3 检索增强（RAG）

平台的“知识库”有两种形态。报告与事实核查使用联网知识库：SearXNG 搜索（优先权威站点）、抓取网页正文、按可信度分层，并为每次运行建立一个临时 Qdrant 集合写入网页分段，运行结束即删除，避免不同运行互相污染；撰稿与核查都在这个集合上用稠密 + BM25 + RRF + 重排检索。问答模块使用用户上传的文档知识库，稠密向量与独立的 BM25 稀疏召回分别从完整索引取候选，再 RRF 融合、LLM 重排，证据不足时有界地改写检索词重检，仍不足则如实拒答。所有网页与文档内容在送入模型前都作为不可信数据处理，提示中明确要求不执行其中夹带的指令。

8.4 关于 MCP

本版本没有使用 MCP（模型上下文协议）。工具层是内部的技能与工具注册表：Agent 只能调用自己定义里声明的技能和工具（如 web_search、page_fetch、number_check），调用面可控、可测试，也减少了外部工具带来的攻击面；代价是接入新的外部工具需要改代码。后续接入思路是把 MCP 服务器的工具包装成技能，在 Agent 的 tools 中声明后由调度器同样纳入资源池与预算管理。这部分尚未实现，这里不作承诺。

8.5 开发过程中的 AI 辅助

项目开发中使用了 AI 编程助手（Claude Code）辅助编写代码、测试与文档，团队负责需求与架构决策、审阅改动、运行真实环境验证。为避免“AI 写报告、AI 自己说好”，本方案书中所有耗时、比例、计数都由 docs/submission/build_data.py 从保存的运行记录与评测报告计算，再填入文档；演示视频的旁白数字也来自同一份数据。

8.6 数据与使用范围

系统使用公开网页和用户自己上传的文档。报告统一披露方法、检索词、阅读网页数、数据点保留与丢弃数、使用的模型和时间；没有把握的内容写“公开资料中未找到”或“单一来源”，不用模型常识去补。用户账户、对话和运行记录保存在自部署的数据库中，系统不用它们训练模型；请求会发送给所配置的模型服务商，对方如何处理取决于其服务条款。平台里的“已核实”是系统按规则给出的判断，不是事实的终审；每条结论保留来源编号与原文出处，需要的人可以自己核对。
